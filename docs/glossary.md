# Cloud-Native & Platform Engineering Glossary

A curated glossary defining core terminology used throughout Terraform, Ansible, Kubernetes, and the broader Cloud-Native ecosystem.

---

### 1. Declarative Configuration
A model where you define the **desired end-state** of your infrastructure or application, and the system automatically determines the necessary steps to reach that state.
* *Example*: Terraform HCL manifests or Kubernetes YAML resource declarations.

### 2. Imperative Configuration
A model where you write explicit step-by-step instructions or commands detailing **how** to construct the environment.
* *Example*: A Bash script running commands sequentially (`apt install`, `mkdir`, `chown`).

### 3. Infrastructure as Code (IaC)
The management and provisioning of infrastructure through machine-readable definition files, rather than physical hardware configuration or interactive configuration tools.
* *Example*: Managing AWS or Proxmox virtual resources via Terraform files checked into a Git repository.

### 4. State File
A record managed by Terraform that maps real-world infrastructure resources to your configuration files. It tracks metadata and resource dependencies to determine what changes must be applied during execution.
* *Warning*: Contains plain-text secrets and should never be committed to Git.

### 5. Playbook
An Ansible file containing one or more "plays" which orchestrate a list of tasks against designated host groups defined inside the inventory. Written in clean YAML.

### 6. Inventory
A configuration file or script defining the target servers, IP addresses, authentication keys, and group mappings that Ansible will manage. Can be static (INI/YAML) or dynamically generated by external API scripts.

### 7. Idempotency
A property of an operation where it can be applied multiple times without changing the result beyond the initial application. 
* *Example*: In Ansible, running a task to ensure a package is installed will only run `apt-get install` if the package is missing, otherwise it completes immediately with `ok` and makes no system changes.

### 8. Container Orchestration
The automated management of container lifecycles, including scaling out containers, load-balancing traffic, self-healing, rolling upgrades, and provisioning storage across a cluster of hardware hosts.

### 9. Pod
The smallest deployable unit of computing that you can create and manage in Kubernetes. It represents a single instance of a running process and can contain one or more tightly coupled application containers.

### 10. Deployment
A Kubernetes resource controller that provides declarative updates for Pods and ReplicaSets, ensuring the requested number of healthy pod replicas are running across the cluster nodes.

### 11. Service
An abstract way to expose an application running on a set of Pods as a network service. It creates a stable, single IP address and DNS name to route traffic to dynamic, ephemeral Pods.

### 12. Ingress Controller
A specialized reverse proxy and load balancer that runs inside a Kubernetes cluster. It orchestrates incoming HTTP and HTTPS traffic from outside the cluster to internal Services based on domain names and paths.

### 13. Helm Chart
A pre-packaged collection of parameterized Kubernetes manifests that can be versioned, customized, and deployed onto a cluster as a single release unit using the Helm package manager.
